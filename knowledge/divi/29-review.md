# Review

## Purpose

This document defines how to review Divi work — whether hand-built by a developer or
generated by an agent — before it ships. It gives the reviewer a concrete order of checks
that catches the failures unique to Divi: structural corruption, asset bloat, update-unsafe
code, and inaccessible or insecure output. It pairs with the [ai-review-checklist](99-ai-review-checklist.md),
which is the fast, itemized form of this process.

Review is the last gate. On client sites it is often the only gate, because the client cannot
evaluate the build themselves.

## Why It Matters

Divi failures are the kind that pass a casual look and fail later: a page that renders fine
but whose builder won't open, a layout that is 4 MB, custom CSS that a Divi update will erase,
or content hidden client-side that a scraper still sees. A review that only looks at the
rendered page misses all of these. A structured review — checking the content model, the
assets, the code location, and the front end — is what stops those from reaching production.

## Core Principles

- **Review the model, not just the render.** Confirm the layout is valid section → row →
  column → module and that the Visual Builder actually opens the page. A page can look right
  and still be corrupt.
- **Check where code lives, not just what it does.** Custom PHP/CSS/JS must be in a child theme
  and enqueued; parent-theme or Code-module code fails review regardless of correctness.
- **Verify on the real front end.** The builder preview differs from the rendered site; review
  the logged-out, cached front end at each breakpoint.
- **Weigh the page.** Performance is a review criterion, not an afterthought — check asset
  weight and Core Web Vitals. See [performance](10-performance.md).
- **Non-functionals are pass/fail.** Accessibility and security are not "nice to have" at
  review; a build that fails them is not done. See [accessibility](12-accessibility.md),
  [security](19-security.md).

## Best Practices

- **Open the Visual Builder** on changed pages to confirm the content model is intact and
  loads without errors — the single fastest corruption check.
- **Diff the reuse story:** are repeated styles presets/global, or duplicated inline CSS? Flag
  duplication that will become maintenance debt.
- **Confirm code placement:** all custom code in a child theme, enqueued with dependencies;
  reject `<script>`/`<style>` in Code modules and any parent-theme edits.
- **Measure the page:** run a Lighthouse/PageSpeed pass; flag oversized images, unused CSS/JS,
  and missing lazy-loading against a budget.
- **Test responsiveness** at each breakpoint on the front end, not only in the builder.
- **Run accessibility checks:** headings order, alt text, color contrast, keyboard navigation,
  and that "hidden" content is not merely CSS-hidden.
- **Check security/update safety:** no secrets in Code modules, `unfiltered_html` not granted
  to editors, and Divi/plugins current.

## Examples

**Good Example** — a review that catches a real defect

```
Review of "Services" page change:
  [x] Visual Builder opens the page without console errors
  [!] Found 12 buttons with identical inline CSS in Advanced tabs
      -> REJECT: convert to a shared preset (one edit vs twelve)
  [!] Custom animation pasted as <script> in a Code module
      -> REJECT: enqueue from the child theme instead
  [x] Front end verified at 320 / 768 / 1440; images lazy-loaded

// WHY: each finding maps to a concrete, actionable fix — not a vague "looks off".
```

**Bad Example** — a shallow review that passes broken work

```
"Looked at the page in Chrome, it renders fine. Approved."

// WHY it's wrong: never opened the builder (could be corrupt), never checked
// where the custom code lives (parent theme?), never measured weight or tested
// mobile/a11y. The defects that matter in Divi are exactly the ones this misses.
```

## Common Mistakes

- Reviewing only the rendered page and never opening the Visual Builder to confirm integrity.
- Passing duplicated inline CSS instead of requiring presets/global modules.
- Ignoring where custom code lives, letting parent-theme edits or Code-module scripts through.
- Skipping performance measurement, so a bloated page ships.
- Treating accessibility and security as optional at review.
- Testing only in the builder, missing front-end and responsive differences.

## Production Tips

- Keep the review checklist in the PR/handoff template so no step is skipped under deadline.
- Record page weight and Lighthouse scores at review; regressions on the next change are then
  obvious.
- Re-review after any Divi/plugin update on staging — updates can change render output.

## AI Review Checklist

- Does the Visual Builder open every changed page without errors (model intact)?
- Are repeated styles presets/global rather than duplicated inline CSS?
- Is all custom code in a child theme and enqueued, not in the parent or a Code module?
- Was the front end verified at each breakpoint, with page weight/Core Web Vitals measured?
- Do accessibility and security checks pass, with no content merely CSS-hidden?
