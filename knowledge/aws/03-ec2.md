# EC2

## Purpose

This document defines how to run virtual-machine compute correctly on **Amazon EC2**:
instance selection, security groups, IAM instance roles, storage, and the patterns that
keep instances secure, available, and cost-efficient. It exists so an agent does not launch
a box that is publicly exposed, un-patched, or carrying long-lived credentials.

EC2 instances are *zonal* — an instance lives in exactly one Availability Zone. Availability
comes from running many of them across AZs behind a load balancer, never from one big box.

## Why It Matters

EC2 is where the two most expensive AWS mistakes meet: security and cost. A security group
opened to `0.0.0.0/0` on port 22 or 3389 is scanned and attacked within minutes. An instance
carrying static AWS keys turns one compromise into an account compromise. And because EC2 is
billed per second while it runs, an oversized or forgotten fleet quietly becomes the largest
line on the bill. Unlike managed services, EC2 leaves patching, hardening, and failover
entirely to you.

## Core Principles

- **Instances are cattle, not pets.** Treat any instance as disposable and reproducible from
  an AMI plus user-data or configuration management. Never hand-configure a box you cannot
  recreate.
- **No SSH from the internet.** Reach instances through **SSM Session Manager**, which needs
  no open inbound port, no bastion, and logs every session. Keep security groups closed
  inbound by default.
- **Attach a role, not keys.** Give the instance an IAM instance profile so applications get
  short-lived credentials automatically. Never bake access keys into an AMI or user-data.
- **Spread across AZs behind a load balancer.** Real availability is N instances in ≥2 AZs
  fronted by an ELB and managed by an Auto Scaling group.
- **Right-size, then buy commitment.** Pick the smallest instance family that meets the
  workload, then cover the steady-state baseline with Savings Plans and burst with Spot.

## Best Practices

- Use the latest-generation Graviton (ARM) instances where the workload supports them —
  they are cheaper per unit of performance than x86 equivalents.
- Encrypt every EBS volume (enable account-level EBS encryption by default) and use `gp3`,
  which is cheaper and lets you tune IOPS independently of size.
- Enforce **IMDSv2** (`http_tokens = "required"`) to block the SSRF-to-credential-theft
  attack that IMDSv1 allows.
- Put application instances in **private subnets**; expose only the load balancer publicly.
- Automate patching with SSM Patch Manager or, better, bake immutable AMIs and roll the
  fleet rather than patching in place.
- Use Spot Instances for fault-tolerant and batch work (up to ~90% cheaper), and Auto
  Scaling to match capacity to demand.

## Examples

**Good Example** — private instance, IMDSv2, instance role, no keys (Terraform)

```hcl
resource "aws_instance" "app" {
  ami                    = data.aws_ami.al2023.id
  instance_type          = "t4g.small"          # Graviton: cheaper per perf
  subnet_id              = aws_subnet.private.id # no public IP
  vpc_security_group_ids = [aws_security_group.app.id]
  iam_instance_profile   = aws_iam_instance_profile.app.name # role, not keys

  metadata_options {
    http_tokens = "required" # IMDSv2 only -> blocks SSRF credential theft
  }
  root_block_device {
    encrypted   = true
    volume_type = "gp3"
  }
}
```

**Bad Example** — public box, SSH to the world, hardcoded keys

```hcl
resource "aws_instance" "app" {
  ami                         = "ami-12345678"
  instance_type               = "m5.4xlarge"    # oversized "just in case"
  associate_public_ip_address = true            # directly on the internet
  # user_data bakes in AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY -> leaked on first compromise
}

resource "aws_security_group_rule" "ssh" {
  type        = "ingress"
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"] # SSH open to the entire internet -> scanned in minutes
}
```

## Common Mistakes

- Opening port 22/3389 to `0.0.0.0/0` instead of using SSM Session Manager.
- Storing static AWS credentials on the instance rather than attaching an instance role.
- Leaving IMDSv1 enabled, exposing credentials to any SSRF vulnerability in the app.
- Running one large instance instead of several small ones across AZs — a single point of
  failure and harder to scale.
- Oversizing "to be safe" and never revisiting, or leaving dev instances running nights and
  weekends.
- Treating an instance as a pet: patching by hand and being unable to recreate it.

## Production Tips

- Enable the EC2 instance connect endpoint or SSM for break-glass access; delete standing
  SSH keys entirely.
- Use Auto Scaling health checks tied to the load balancer so unhealthy instances are
  replaced automatically.
- Schedule dev/test fleets to stop outside business hours; it is often the single largest
  easy cost saving.
- Ship application and system logs to CloudWatch Logs via the agent so a terminated instance
  does not take its logs with it.

## AI Review Checklist

- Are security groups closed inbound, with no `0.0.0.0/0` on SSH/RDP?
- Does the instance use an IAM instance profile instead of static keys?
- Is IMDSv2 required (`http_tokens = "required"`)?
- Are application instances in private subnets, with only the ELB public?
- Are EBS volumes encrypted and using `gp3`?
- Is the workload spread across ≥2 AZs under an Auto Scaling group?
- Is the instance right-sized, with commitment/Spot pricing applied where appropriate?
