# Block Editor

## Purpose

This document defines how to build for the block editor: registering a block through
`block.json`, choosing between static and dynamic rendering, using block supports instead of
custom attributes, and handling the deprecations that changing a block requires.

A block is a content format, not just a UI component. Its attributes are written into every
post that uses it, which makes the initial design a long-term commitment.

---

## Core Principle

**A block's markup is stored content.** For a static block, the output of `save` is serialized
into `post_content`. Changing that output without a deprecation entry invalidates every
existing post that contains the block — the editor shows "this block contains unexpected or
invalid content" on content nobody touched.

That single fact drives every recommendation below: prefer supports over custom attributes,
prefer dynamic rendering when the markup will evolve, and always ship deprecations.

---

## Registration Through `block.json`

`block.json` is the single source of truth: PHP, JavaScript, and the block directory all read
the same file.

```json
{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "acme/event-card",
  "title": "Event Card",
  "category": "widgets",
  "icon": "calendar-alt",
  "description": "Displays a single event with its date and venue.",
  "textdomain": "acme-events",
  "attributes": {
    "eventId": { "type": "number" },
    "showVenue": { "type": "boolean", "default": true }
  },
  "supports": {
    "html": false,
    "spacing": { "margin": true, "padding": true },
    "color": { "background": true, "text": true },
    "typography": { "fontSize": true }
  },
  "editorScript": "file:./index.js",
  "editorStyle": "file:./index.css",
  "style": "file:./style-index.css",
  "render": "file:./render.php"
}
```

```php
// PHP registration reads everything from block.json.
add_action( 'init', 'acme_register_blocks' );

function acme_register_blocks(): void {
	register_block_type( ACME_EVENTS_PATH . 'build/event-card' );
}
```

`"render": "file:./render.php"` (WordPress 6.1+) declares a dynamic block without a PHP
callback — the file receives `$attributes`, `$content`, and `$block`.

Build with `@wordpress/scripts`, which compiles JSX and copies `block.json` into `build/`:

```json
{ "scripts": { "start": "wp-scripts start", "build": "wp-scripts build" } }
```

## Static or Dynamic

| | Static | Dynamic |
|---|---|---|
| Markup lives in | `post_content` | A PHP render callback |
| Changing markup | Requires a deprecation | Just deploy |
| Live data | Stale — frozen at save | Always current |
| Cost | Free at render | PHP runs on every request |

Use **dynamic** whenever output depends on anything outside the post: queries, user state,
dates, options. Use **static** for self-contained presentational markup where render cost
matters.

**Good Example** — dynamic render, escaped, no query in the template

```php
<?php
// render.php — $attributes, $content, $block are in scope.
defined( 'ABSPATH' ) || exit;

$event_id = isset( $attributes['eventId'] ) ? absint( $attributes['eventId'] ) : 0;
$event    = $event_id ? get_post( $event_id ) : null;

if ( ! $event || 'publish' !== $event->post_status ) {
	return;   // render nothing rather than a broken card
}

$start = get_post_meta( $event_id, '_acme_event_start', true );
?>
<div <?php echo get_block_wrapper_attributes(); ?>>
	<h3 class="acme-event-card__title">
		<a href="<?php echo esc_url( get_permalink( $event ) ); ?>">
			<?php echo esc_html( get_the_title( $event ) ); ?>
		</a>
	</h3>

	<?php if ( $start ) : ?>
		<time datetime="<?php echo esc_attr( $start ); ?>">
			<?php echo esc_html( wp_date( get_option( 'date_format' ), strtotime( $start ) ) ); ?>
		</time>
	<?php endif; ?>
</div>
```

`get_block_wrapper_attributes()` is required, not cosmetic: it emits the classes and inline
styles generated by block supports. Without it, every alignment, color, and spacing setting
the user chose is discarded.

## Prefer Supports Over Attributes

Block supports give you editor UI, theme integration, and forward compatibility for free.
Hand-rolled attributes give you maintenance.

**Bad Example**

```json
{
  "attributes": {
    "backgroundColor": { "type": "string" },
    "paddingTop": { "type": "number" },
    "fontSize": { "type": "number" }
  }
}
```

Now you own three controls, three sets of CSS, and three migration paths — and none of them
respect the theme's palette or `theme.json`.

**Good Example**

```json
{
  "supports": {
    "color": { "background": true, "text": true },
    "spacing": { "padding": true, "margin": true },
    "typography": { "fontSize": true, "lineHeight": true }
  }
}
```

The editor renders the standard panels, values come from the theme's presets, and the markup
stays compatible as core evolves. See [Block Themes](17-block-themes.md).

## The Edit Component

```jsx
import { useBlockProps, InspectorControls } from '@wordpress/block-editor';
import { PanelBody, ToggleControl } from '@wordpress/components';
import { useSelect } from '@wordpress/data';
import { __ } from '@wordpress/i18n';

export default function Edit( { attributes, setAttributes } ) {
	const { eventId, showVenue } = attributes;
	const blockProps = useBlockProps();

	// Read through the data layer, not a bare fetch — it is cached and reactive.
	const event = useSelect(
		( select ) => ( eventId ? select( 'core' ).getEntityRecord( 'postType', 'acme_event', eventId ) : null ),
		[ eventId ]
	);

	return (
		<>
			<InspectorControls>
				<PanelBody title={ __( 'Display', 'acme-events' ) }>
					<ToggleControl
						label={ __( 'Show venue', 'acme-events' ) }
						checked={ showVenue }
						onChange={ ( value ) => setAttributes( { showVenue: value } ) }
					/>
				</PanelBody>
			</InspectorControls>

			<div { ...blockProps }>
				{ event ? event.title.rendered : __( 'Select an event…', 'acme-events' ) }
			</div>
		</>
	);
}
```

Attributes are the source of truth. Copying them into local state produces two truths that
drift apart — see [React — State](../react/06-state.md).

## Deprecations

Changing a static block's `save` output without a deprecation breaks existing content:

```js
registerBlockType( metadata.name, {
	edit: Edit,
	save: Save,                 // current markup
	deprecated: [
		{
			attributes: v1Attributes,
			save: V1Save,       // the OLD markup, kept verbatim
			migrate: ( attributes ) => ( {
				...attributes,
				showVenue: attributes.displayVenue ?? true,   // rename handled here
			} ),
		},
	],
} );
```

The editor tries each deprecation in order until one parses the stored markup. Deprecations
accumulate — they are removed only when you are certain no content uses them, which in
practice means after a content migration.

## Patterns, Variations, and Styles

Not every requirement needs a new block type. In increasing order of cost:

```php
// A block style: one extra class, no new block.
register_block_style( 'core/quote', array(
	'name'  => 'acme-pullquote',
	'label' => __( 'Pull quote', 'acme-events' ),
) );

// A pattern: a prearranged composition of existing blocks.
register_block_pattern( 'acme/event-hero', array(
	'title'      => __( 'Event hero', 'acme-events' ),
	'categories' => array( 'header' ),
	'content'    => '<!-- wp:cover … --><!-- /wp:cover -->',
) );
```

A block variation (`registerBlockVariation`) preconfigures an existing block with different
attributes. Reach for a new block type only when the behavior genuinely does not exist yet.

---

## Common Mistakes

- **Changing `save` output without a deprecation**, invalidating published content.
- **Omitting `get_block_wrapper_attributes()`** in a dynamic render, discarding all supports.
- **Custom attributes duplicating supports**, losing theme integration.
- **Not escaping in `render.php`** — attributes are user-authored input.
- **Queries in the render callback** without caching, running on every page view.
- **Registering the block only in JS**, so PHP and the block directory never see it.
- **Copying attributes into local state** in `edit`.
- **A new block type** where a pattern, variation, or style would do.
- **`"supports": { "html": true }`** (the default) on a block whose markup you control,
  letting editors hand-edit it into invalidity.

---

## Verification Checklist

- Is the block registered from `block.json`, with PHP reading the same file?
- Is the static/dynamic choice deliberate, given whether output depends on live data?
- Are appearance controls expressed as supports rather than custom attributes?
- Does the dynamic render escape every value and call `get_block_wrapper_attributes()`?
- Do markup changes to static blocks ship with a deprecation and a `migrate`?
- Are strings translated with the block's text domain?
- Could this be a pattern, variation, or block style instead of a new block type?

---

## Summary

Register through `block.json`, treat attributes and saved markup as a content contract, lean
on block supports rather than reinventing controls, escape everything in dynamic renders, and
never change static output without a deprecation.
